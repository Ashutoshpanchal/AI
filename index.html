⛨

Guardrails

Permission checks the action and the resource. A live connection is not enough.

  • Reads are allowed. Production writes, DAG triggers, and grants are not.
  • A missing permission goes to the Jira comment. It does not go back to the planner.
  • A failed proof goes back to the Solution Agent with a different hypothesis, up to three times.
  • After the third miss, the report says the cause is unproved and includes no diff.
  • Secrets stay in the secret store. They are not written into the prompt or Postgres.
⌘

MCP and scope

Each playbook names the connections it needs. The scope is the resource, not the whole system.

  • Jira. Read the assigned ticket. Write one comment with the report link.
  • dbt. manifest.json and run_results.json. No dbt run in production.
  • Snowflake. Read-only role, statement timeout, credit cap. No insert, update, delete, merge, copy, or drop.
  • Airflow. Task state and logs. No trigger, clear, retry, or backfill.
  • GitHub. The dbt repo and the DAG repo, the file the plan named. A branch and a diff. No push to the default branch.
  • Source API. The contract or the day named in the ticket.
▤

Storage

The warehouse stays the warehouse. The run is stored beside it.

  • Postgres. The run, the asset graph, the plan, the evidence list, and the 1–5 rating.
  • pgvector. Ticket text, logs, and SQL, so a later run can find a similar incident.
  • GitHub. The diff, on a branch. The report links to it.
  • Secret store. Source credentials. The model never sees them.
  • Snowflake. Business data. The agent reads it and does not copy the table into Postgres.
There is no queue worker on this path. FastAPI accepts the assignment and the Solution Agent starts the plan.
